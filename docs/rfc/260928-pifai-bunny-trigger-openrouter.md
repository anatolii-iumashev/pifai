# RFC: Перенос ПиФ на Bunny, Trigger.dev и OpenRouter

## Вводные

ПиФ уже имеет статическую базу знаний и Telegram-бота, но сайт публикуется через GitHub Pages, а Cloudflare Worker одновременно принимает webhook, ищет статьи, хранит историю и обращается к Groq. Переносим сайт на Bunny Storage/CDN, входящий Telegram webhook — на Bunny Edge Script, а обработку диалога и отправку ответа — в Trigger.dev с OpenRouter. Одновременно обновляем сборку базы знаний и измеряем качество ответов на фиксированном наборе вопросов: простая смена инфраструктуры качества консультаций не даст.

## Назначение и цели

- Переподключить существующего Telegram-бота без смены его идентичности и с возможностью возврата прежнего webhook до завершения миграции.
- Получать более полезные, эмпатичные и проверяемые ответы по актуальной wiki: релевантные страницы, рабочие ссылки, отсутствие выдуманных цитат, корректная реакция на кризисные сообщения.
- Оставить Bunny только публичной границей (сайт и приём событий), Trigger.dev — местом исполнения консультаций, OpenRouter — провайдером моделей. Секреты модели и содержание диалогов не попадают в статические файлы или логи webhook.
- Сохранить команды `/start`, `/help`, `/clear` и ограниченную историю диалога, исключить двойные ответы при повторах Telegram и повторных запусках задач.

**Кого касается:** пользователей бота и wiki, редактора базы знаний, владельца бота и оператора инфраструктуры. Ревью: владелец ПиФ и разработчик миграции.

## Составляющие и особенности

Разбиение идёт по последовательным границам одного запроса: **публикация знаний → приём события → консультация → сохранение и доставка**. Каждая граница имеет свой артефакт и контракт.

### 1. Публикация сайта и знаний

- Сохранить Astro/Starlight и текущую структуру `src/content/docs/`. Собирать сайт с корнем `/` и окончательным `site` URL Bunny; публиковать `dist/` в отдельные Bunny Storage Zone и Pull Zone. Проверить глубинные ссылки, картинки, canonical, sitemap, `/404.html`, HTTPS и cache policy. Для хэшированных ассетов — длительный TTL, для HTML — короткий; загрузить ассеты до HTML и очищать CDN после публикации, как у [сайта summ-bbot](../../../summ-bbot/docs/specs/site.md).
- В том же CI/build получать **версионированный индекс знаний** из фактически публикуемых страниц `.md` и `.mdx` и необходимых цитат YAML. Индекс содержит `id`, название, раздел, нормализованный текст, канонический URL, `contentHash`, `buildId`. Для цитат из YAML индексировать исходную запись и ссылку на реально опубликованную тематическую страницу, не придумывая URL для YAML-файла. Исключить `index.md`, `log.md`, служебные и дублирующие фрагменты. При ошибке парсинга или несуществующей ссылке сборка падает.
- Публиковать индекс как неизменяемый артефакт конкретной сборки и указатель на текущую версию. Trigger.dev загружает индекс версии на старте/при смене версии и сверяет `buildId`; публикация сайта и индекса должна быть согласованной. Не встраивать весь корпус в Edge Script или каждый Telegram payload.
- `KNOWLEDGE_BASE_URL` и ссылки в ответах должны вести на новый публичный домен; редирект со старых GitHub Pages URL на новый адрес — по возможности старой площадки. Смену домена не смешивать с редактурой содержания wiki.

### 2. Приём Telegram на Bunny

- Один **Bunny Edge Script** на HTTPS-маршруте `/webhook` принимает только `POST`, сверяет `X-Telegram-Bot-Api-Secret-Token` до разбора тела, ограничивает размер запроса, валидирует `update_id`, `message`, `chat.id` и поддерживаемые типы сообщений. `GET /health` показывает лишь состояние приёмника, без секретов и личных данных. Публичный сайт обслуживает отдельная Pull Zone; проксирование webhook через кеширующий статический CDN не допускается. [Bunny подтверждает поддержку standalone Edge Scripts для webhook и HTTP API](https://docs.bunny.net/docs/access-edge-database-with-turso).
- Скрипт создаёт компактный `ConsultationJob` (`updateId`, `chatId`, `messageId`, `userId`, `text`, `receivedAt`, `schemaVersion`) и вызывает REST trigger задачи с серверным ключом. В v1 — личные текстовые чаты и команды `/start`, `/help`, `/clear`; для групп, медиа и неподдерживаемых событий задаётся безопасное явное поведение, без отправки содержания в OpenRouter. Telegram получает 2xx **только после успешного enqueue**; при ошибке Trigger.dev — 5xx для повторной доставки. Telegram повторяет webhook после ответа вне диапазона 2xx и поддерживает секретный заголовок: [Bot API](https://core.telegram.org/bots/api#setwebhook).
- Идемпотентность постановки: стабильный ключ `pifai:tg:<update_id>` с TTL, покрывающим окно повторной доставки; повтор одного update возвращает тот же run. Edge Script не импортирует индекс wiki, LLM, хранилище диалогов и код отправки. В нём хранятся только секрет Telegram webhook и ключ запуска Trigger.dev. Разделение соответствует схеме summ-bbot, но адаптируется к runtime и API Bunny, а не копирует Cloudflare handler.

### 3. Консультация в Trigger.dev и OpenRouter

- Задача `consult-telegram` валидирует payload повторно, выполняет команды и полную цепочку для текста: загрузка истории → распознавание кризисного запроса → поиск по версии индекса → сборка контекста → OpenRouter → проверка ответа и источников → подготовка Telegram-сообщения. Для одного диалога задачи идут последовательно (`concurrencyKey` по `chatId` либо эквивалентный механизм) с общим ограничением параллельности и затрат. Trigger.dev поддерживает очереди и ключи параллельности: [документация продукта](https://trigger.dev/product/concurrency-and-queues).
- Базовый поиск на старте миграции — локальный индекс с нормализацией русского текста и лексическим ранжированием (например, BM25); `topK`, длина чанка и бюджет контекста настраиваются. Семантический или гибридный поиск добавлять только если он улучшает размеченный набор вопросов. Учитывать предыдущую реплику пользователя для follow-up вопросов. Источники передавать модели как **недоверенные данные** со стабильными ID, а не как инструкции.
- OpenRouter вызывается только из Trigger.dev. `OPENROUTER_API_KEY`, модель, лимиты токенов, таймаут и резервная модель задаются окружением. Выбирать модель по результату сравнительной оценки; не закреплять название из `PRODUCT.md` без проверки доступности и качества. Логировать идентификатор модели, версию индекса, задержку и расход токенов, но не полный текст вопросов и ответов. До релиза проверить, как Trigger.dev хранит payload задач и кто видит его в dashboard: отсутствие текста в `console.log` не означает отсутствия текста в истории запусков.
- Ответ на русском, с эмпатией и конкретным следующим шагом, без диагноза и категоричного назначения. Утверждения «по базе знаний» сопровождаются ссылками только из найденных источников; если релевантного материала нет, бот прямо говорит об этом и не придумывает цитату. Ссылки сверяются программно по ID/URL из индекса до отправки. Кризисные сигналы обрабатываются **до обычной генерации**: короткий поддерживающий ответ, рекомендация обратиться за срочной помощью и к человеку; конкретные контакты сверяются с актуальными официальными источниками для выбранной географии перед релизом. Психологические правила и промпты из `bot/src/prompts.ts` переносятся с ревизией, а не механически.
- Транзитные ошибки OpenRouter повторяются с backoff и пределом попыток; ошибки валидации, отсутствие источников и небезопасный ответ не запускают бесконечные повторы. После исчерпания попыток пользователь получает одно нейтральное сообщение об ошибке.

### 4. История диалога и доставка

- История нужна между задачами и не может жить в памяти Edge Script или Trigger run. Для v1 использовать транзакционное хранилище с уникальными ключами `(platform, update_id)` и `(chat_id, message_id, role)`; рекомендуемая реализация — Postgres, размещение выбирается до delivery с учётом чувствительности переписки. Хранить только необходимые реплики, версии модели/индекса, состояние доставки и срок удаления; по умолчанию сохранить прежний предел: 20 последних сообщений и 7 дней. `/clear` удаляет историю данного личного чата, а не чужие диалоги пользователя. Доступ — только у Trigger.dev по отдельному секрету.
- После генерации атомарно сохранять результат и маркер отправки; повтор запуска сначала проверяет состояние. Telegram Bot API не даёт транзакции с нашей БД, поэтому при сетевом сбое после фактической отправки возможна неопределённость. В реализации предусмотреть стабильное статус-сообщение с последующим `editMessageText` **или** консервативную политику повторной отправки, явно протестировать этот случай и не обещать абсолютное exactly-once. Для длинных ответов — безопасное разбиение под лимит Telegram и резервный plain text при ошибке форматирования ([Bot API, `sendMessage`](https://core.telegram.org/bots/api#sendmessage)).
- Старое содержимое Cloudflare KV не переносить автоматически: сначала проверить необходимость и правовое основание миграции чувствительной истории. При переключении либо выполнить отдельный проверенный импорт, либо начать новые сессии и заранее сообщить пользователям о сбросе. После стабилизации убрать Worker, KV binding, Groq secrets и старые настройки webhook из активного деплоя; старые ресурсы удалять только после периода отката.

## Критерии приемки (checklist)

### 1. Публикация сайта и знаний

- [ ] Сайт целиком доступен через Bunny по HTTPS; минимум 10 маршрутов из разных разделов, главная, 404, assets и ссылки из Telegram проходят ручную и автоматическую проверку. `site`/canonical/sitemap указывают на новый домен, на нём нет путей с лишним `/pifai`.
- [ ] Один build выпускает сайт и индекс с одинаковым `buildId`; индекс покрывает `.md`, `.mdx` и выбранные цитаты YAML. Сборка падает на битой исходной ссылке, а новая wiki-страница появляется в следующей версии без правки bot-кода.

### 2. Приём Telegram на Bunny

- [ ] Запрос без верного секретного заголовка получает 401 и не создаёт run; неподдерживаемый метод получает 405; невалидный payload не создаёт run.
- [ ] Валидное текстовое сообщение ставит ровно один run; повтор того же `update_id` не создаёт второй run. Ошибка enqueue возвращает 5xx и успешная повторная доставка ставит задачу.
- [ ] `getWebhookInfo` показывает новый Bunny URL и отсутствие растущей очереди ошибок после переключения.

### 3. Консультация в Trigger.dev и OpenRouter

- [ ] Проверены `/start`, `/help`, `/clear`, обычный вопрос, уточняющий вопрос, вопрос без релевантного знания и кризисный сценарий. Ответ не содержит выдуманных цитат и ссылок вне индекса; при отсутствии знания это явно сказано.
- [ ] На заранее размеченных минимум 30 вопросах (теория, применение, follow-up, вне базы, кризис) релевантная страница попадает в top-3 не менее чем в 80% случаев; все опубликованные ссылки разрешаются в 200/корректный редирект. В слепом парном сравнении с текущим ботом минимум 70% обычных ответов оценены не хуже и минимум 50% — лучше по рубрике: эмпатия, конкретность, опора на источник; на кризисном наборе нет критических ошибок. Порог фиксируется до настройки модели.
- [ ] Сбой OpenRouter проходит ограниченные повторы и завершённую ошибку видно в Trigger.dev; webhook при этом уже ответил Telegram и не выполнял LLM-вызов.

### 4. История диалога и доставка

- [ ] Две быстрые реплики одного чата обрабатываются по порядку, `/clear` удаляет только его историю; после 7 дней и за пределами 20 сообщений данные недоступны в активном контексте.
- [ ] Повтор webhook и повтор задачи после сбоя не создают повторной записи в истории; тест сетевой неопределённости доставки документирует ожидаемое поведение. Длинный ответ и ошибка Markdown не оставляют пользователя без читаемого сообщения.
- [ ] В прикладных логах Bunny, Trigger.dev и OpenRouter-инструментации нет текста личных сообщений, ключей и полного payload; секреты находятся только в серверных окружениях. Доступ и срок хранения payload самих Trigger runs проверены отдельно. Решение по старой KV-истории и сроку отката зафиксировано до переключения.

## Дорожная карта

1. **Публикация сайта и знаний.** Согласовать публичный домен, собрать сайт и индекс из одного коммита, развернуть Bunny Storage/Pull Zone, проверить URL и версии. Пока Telegram смотрит на старый webhook.
2. **Приём Telegram на Bunny.** Развернуть Edge Script с секретами в тестовом окружении/на тестовом боте; проверить авторизацию, валидацию, enqueue, ошибки и дубли.
3. **Консультация в Trigger.dev и OpenRouter.** Развернуть `consult-telegram`, обновить retriever и промпты, провести оценку на фиксированном наборе, подобрать модель и бюджет. Продовый бот ещё не переключать, пока критерии качества не выполнены.
4. **История диалога и доставка.** Подключить транзакционное хранилище, проверить порядок сообщений, команды, сроки хранения и сбои отправки. Решить судьбу KV-истории, затем перевести `setWebhook` существующего бота на Bunny без `drop_pending_updates`, проверить `getWebhookInfo` и реальные диалоги. Держать старый Worker готовым к возврату webhook на период наблюдения; после стабилизации удалить активные Cloudflare/Groq зависимости.

## Итого и рекомендации

Перенести публичный сайт и входящий webhook ПиФ на Bunny, выполнять консультации в Trigger.dev через OpenRouter и выпускать версионированный индекс из той же wiki, что видит пользователь. Переключать существующего бота после проверки качества, истории и доставки; улучшение консультаций подтверждать сравнением ответов и валидностью источников, а не самим фактом миграции.

### Открытые вопросы

- Какой окончательный домен ПиФ и где размещать транзакционную историю с учётом географии пользователей, согласия и политики хранения? От этого зависят URL и выбор провайдера Postgres.
- Нужно ли переносить старые диалоги из Cloudflare KV или допустим прозрачный для пользователей сброс при релизе?
- Нужно ли после первой версии отвечать в группах, поддерживать голосовые сообщения или давать веб-чат? Текущий RFC принимает только личный текстовый Telegram-диалог; сайт остаётся базой знаний и точкой входа в бота.
- Кто утверждает кризисные сценарии и актуальные контакты помощи для целевой географии? Без этого критерий кризисной безопасности нельзя закрыть.
- Какой срок хранения и режим доступа к текстовым payload предоставляет выбранный план Trigger.dev? Если нужные ограничения недоступны, нужно уменьшить payload или выбрать допустимую схему до запуска продового бота.
