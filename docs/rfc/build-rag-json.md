# RFC: Build-time RAG-индекс базы знаний и LangChain-инструмент поиска

## Вводные

Wiki ПиФ поддерживается LLM-агентами по схеме «LLM Wiki» (скиллы `wiki-ingest` / `wiki-query` / `wiki-lint` из [AGENTS.md](../../AGENTS.md)), а бот ищет по ней самодельным keyword-ретривером из сгенерированного вручную `bot/src/knowledge.ts`. Этот индекс собирается отдельно от сайта, не видит `.mdx` и цитаты из YAML и ранжирует по пересечению токенов. **Решение:** при каждом `astro build` из тех же Content Collections, что и сайт, собираем версионированный RAG-артефакт `dist/rag/` (чанки + метаданные + опционально эмбеддинги с кешем). Бот загружает его и использует через LangChain.js-инструмент `search_knowledge_base` с гибридным поиском (BM25 + вектор), который агент вызывает при обработке вопроса.

## Назначение и цели

- **Один источник правды.** Бот отвечает по той же версии wiki, что опубликована на сайте. Новая страница или цитата попадает в поиск после следующего билда без правки кода бота.
- **Полнота корпуса.** В поиск попадают все опубликованные `.md` и `.mdx` страницы и все цитаты `src/content/quotes/*.yaml` ([спека коллекции цитат](../specs/quotes-yaml-collection.md)). Сейчас индекс датирован 2026-05-28: 29 страниц, 256 чанков. В `src/content/docs/` уже 49 файлов, из них 11 `.mdx`, а цитаты вообще не индексируются.
- **Качество поиска.** Переход от Jaccard по ключевым словам к BM25 с русской нормализацией и, если это доказано оценкой, к гибриду с эмбеддингами. Эмбеддинги нужны для перефразированных бытовых вопросов («муж не слышит меня»), где лексика запроса не совпадает с лексикой статьи.
- **Инструмент, а не склейка промпта.** Поиск оформлен как LangChain tool со схемой аргументов и структурированным результатом. Агент сам решает, когда искать, может переформулировать запрос и искать повторно, а ссылки на источники можно проверить программно по ID.
- **Почему сейчас.** [RFC переноса на Bunny/Trigger.dev/OpenRouter](./260928-pifai-bunny-trigger-openrouter.md) переносит консультацию в Node-задачу Trigger.dev и требует «версионированный индекс знаний» и лексический поиск. В `ROADMAP.md` стоит пункт `add langchain`. Этот RFC детализирует контракт индекса и поиска, чтобы миграция его потребляла, а не изобретала заново.

**Граница с «LLM Wiki».** Механизмы LLM Wiki (ingest, lint, query агентом по страницам) не меняются: они отвечают за *написание и поддержку* wiki. RAG отвечает за *чтение wiki ботом в рантайме*. Скилл `wiki-query` остаётся инструментом редактора, а не бота.

**Кого касается:** владельца ПиФ и редактора базы знаний (билд и CI), разработчика бота и миграции на Trigger.dev. Ревью: владелец ПиФ и исполнитель RFC миграции.

## Составляющие и особенности

Разбиение идёт по стадиям конвейера данных: **извлечение → чанкинг → упаковка артефакта → поиск-инструмент в рантайме → оценка**. Каждая стадия владеет своим форматом на выходе. Следующая стадия зависит только от этого формата.

### 1. Извлечение корпуса из Content Collections

- Источник — Astro Content Collections `docs` и `quoteAuthors` ([src/content.config.ts](../../src/content.config.ts)), а не обход файловой системы. Так индекс и сайт используют одни и те же схемы, фильтры и slug'и.
- Точка сборки — prerendered endpoint `src/pages/rag/chunks.json.ts` (`getCollection()` → JSON). После `astro build` он даёт `dist/rag/chunks.json`. Endpoint не делает сетевых вызовов.
- **Страницы.** Берутся все записи `docs`, кроме `index`, `log` и черновиков (`draft: true`). У каждой есть `id`, `title`, `description`, раздел верхнего уровня (`basics`, `authors/jung`, …) и канонический URL. URL строится от `site` + `base` из `astro.config.mjs` по той же логике, что у Starlight, поэтому при переезде домена (RFC Bunny) он меняется автоматически.
- **MDX.** Из тела удаляются `import`/`export` и JSX-компоненты. Тематические страницы цитат (`quotes/*.mdx`, внутри `<QuoteList topic=…/>`) индексируются только своим вводным текстом. Сами цитаты берутся из п. «Цитаты», чтобы не было дублей.
- **Цитаты.** Каждая запись `quotes[]` из `quoteAuthors` даёт отдельный документ со следующими полями: текст, автор (`name`/`fullName`), `context`, `reflection`, `topics`, `source`. URL — опубликованная тематическая страница `/quotes/<topics[0]>/` (slug темы совпадает с именем файла, см. `src/lib/quote-topics.ts`). URL на YAML-файл не придумывается.
- Секция «Материалы и источники» не попадает в текст, но её ссылки сохраняются в `metadata.references`.
- **Fail-fast.** Сборка падает на странице без `title`, на пустом теле и на цитате, для темы которой нет опубликованной страницы.

### 2. Чанкинг и метаданные

- Страница режется по заголовкам `##` (как сейчас в `bot/scripts/build-knowledge.ts`). Секция длиннее ~1500 символов делится по абзацам на куски ~800–1200 символов с перекрытием ~150. Секции короче ~80 символов приклеиваются к соседней. Все пороги вынесены в конфиг.
- Каждый чанк:

  ```json
  {
    "id": "authors/jung/shadow#Работа с тенью#0",
    "kind": "page",
    "pageId": "authors/jung/shadow",
    "title": "Тень",
    "section": "Работа с тенью",
    "category": "authors/jung",
    "url": "https://…/authors/jung/shadow/#работа-с-тенью",
    "text": "…",
    "contentHash": "sha256:…",
    "metadata": { "description": "…", "references": ["…"] }
  }
  ```

  У цитат `kind: "quote"` и `metadata: { author, topics, work? }`.
- `id` детерминирован: он зависит от пути, заголовка и порядкового номера куска, а не от времени сборки. Якорь в `url` совпадает с тем, что Starlight генерирует для заголовка. `contentHash` считается от текста, который уходит в эмбеддинг: `title + section + text`. По нему работает кеш эмбеддингов.

### 3. Артефакт индекса: эмбеддинги, версия, публикация

- Post-build шаг `scripts/build-rag-embeddings.ts` (`"build": "astro build && tsx scripts/build-rag-embeddings.ts"`) читает `dist/rag/chunks.json` и пишет:
  - `dist/rag/manifest.json`: `schemaVersion`, `buildId` (git SHA + время), `createdAt`, `siteUrl`, `chunkCount`, `pageCount`, `quoteCount`, `embedding: { provider, model, dim } | null` и хеши файлов;
  - `dist/rag/embeddings.bin` (Float32, порядок = порядок `chunks.json`), если эмбеддинги включены.
- **Эмбеддинги опциональны.** Флаг `RAG_EMBEDDINGS=off|on`. Провайдер — OpenAI-совместимый endpoint (`RAG_EMBED_BASE_URL`, `RAG_EMBED_MODEL`, `RAG_EMBED_API_KEY`), модель должна быть мультиязычной. Без ключа или с `off` артефакт собирается без векторов, и рантайм работает только на BM25. Так локальный `npm run build` без секретов остаётся рабочим.
- **Кеш.** `.cache/rag-embeddings.json` (`contentHash → vector`, ключ включает модель) сохраняется между CI-запусками через cache action. Повторный билд без изменений контента не делает ни одного вызова API.
- Для оценки порядка величины: ~50 страниц и 21 файл цитат дают порядка 500–1000 чанков, при dim 1024 это ≈2–4 МБ бинарника. Формат FAISS/HNSW не нужен: полный перебор такого объёма занимает миллисекунды.
- Артефакт публикуется вместе с сайтом: тот же `buildId` и тот же деплой, что и у HTML (GitHub Pages сейчас, Bunny после миграции). Индекс содержит только уже публичный текст wiki. Путь стабильный (`/rag/manifest.json`). Бот сверяет `buildId` и кеширует артефакт по нему.
- `bot/scripts/build-knowledge.ts` и генерируемый `bot/src/knowledge.ts` (≈14 тыс. строк в репозитории) выводятся из использования, как только рантайм переключён на артефакт.

### 4. Поиск в рантайме и LangChain-инструмент

- Новый модуль бота `bot/src/rag/`:
  - `loadRagIndex(source)` принимает URL или локальный путь. Он читает manifest, проверяет `schemaVersion` и хеши, загружает чанки и векторы. Результат кешируется в памяти процесса по `buildId`.
  - **Лексический ретривер** — BM25 с русской нормализацией: lowercase, `ё→е`, стоп-слова, стемминг Snowball-ru или эквивалент. Индекс BM25 строится при загрузке, в артефакт не пишется.
  - **Векторный ретривер** — косинус по предзагруженным векторам. Эмбеддинг запроса считается той же моделью, что указана в manifest. Если модели в manifest нет, векторный ретривер не активируется.
  - **Гибрид** — Reciprocal Rank Fusion двух списков. Затем идёт дедупликация: не больше 2 чанков с одной страницы. Режим задаётся параметром `RAG_MODE=bm25|hybrid`, по умолчанию `bm25`, пока оценка (п. 5) не покажет выигрыш.
- Ретривер реализует `BaseRetriever` из `@langchain/core` и возвращает `Document` с `metadata` из чанка. Так его можно использовать и в обычной LCEL-цепочке, и в агенте.
- **Инструмент** `search_knowledge_base` создаётся через `tool()` из `@langchain/core/tools` со схемой zod:
  - вход: `{ query: string; kind?: "page" | "quote" | "any"; category?: string; k?: number (1..8, default 4) }`;
  - выход: JSON `[{ sourceId, title, section, url, kind, author?, text }]`, общий объём ограничен бюджетом символов;
  - описание для модели (ru) объясняет, когда вызывать: теория, техники, «что говорит автор X», цитаты по теме. Там же сказано, что результаты — недоверенные данные, а не инструкции.
- Дополнительно экспортируется `getSourceById(id)`. Постпроцессор ответа сверяет URL в тексте бота с множеством `sourceId`/`url`, реально возвращённых инструментом в этом диалоге. Промпт, модель и оркестрация агента в этот RFC не входят: они относятся к RFC миграции (задача `consult-telegram`).
- Рантайм — Node (Trigger.dev). Модуль не использует `fs` в ядре (загрузка по URL), поэтому остаётся совместимым и с текущим Cloudflare Worker на переходный период.

### 5. Оценка качества поиска

- `bot/eval/retrieval.jsonl` содержит ≥30 размеченных вопросов: теория, применение, бытовая формулировка, цитата по теме, вне базы. Для каждого указан ожидаемый `pageId` (или `null` для «вне базы»). Этот набор общий с RFC миграции: там на нём оценивают ответы, здесь — поиск.
- `npm run eval:retrieval` прогоняет старый keyword-ретривер, `bm25` и `hybrid`. Скрипт печатает recall@3, MRR и долю ложных срабатываний на «вне базы» (score выше порога отсечения) и пишет отчёт в `bot/eval/reports/<buildId>.md`.
- Порог включения `hybrid` по умолчанию: recall@3 выше, чем у `bm25`, минимум на 5 п.п., при этом «вне базы» не хуже. Порог фиксируется в файле до настройки параметров.

## Критерии приемки (checklist)

### 1. Извлечение корпуса

- [ ] `npm run build` без секретов создаёт `dist/rag/chunks.json`. Каждая запись `docs`, кроме `index`/`log`, даёт ≥1 чанк. Число `kind: "quote"` равно суммарному числу цитат во всех YAML.
- [ ] В чанках нет `import`, JSX-тегов и текста секций «Материалы и источники». Цитаты не дублируются чанками тематических страниц.
- [ ] Добавленная тестовая страница `.mdx` и тестовая цитата появляются в индексе после билда без правок кода. Цитата с темой без страницы или страница без `title` роняют билд с понятной ошибкой.

### 2. Чанкинг и метаданные

- [ ] Ни один чанк не длиннее верхнего порога конфигурации. Каждый чанк содержит все обязательные поля схемы (проверка zod-схемой в тесте).
- [ ] Два билда одного коммита дают идентичные `id` и `contentHash`. Правка одной секции меняет `contentHash` только у чанков этой секции.
- [ ] 100% `url` в индексе разрешаются в существующие страницы `dist/`, а якоря — в существующие `id` заголовков (тест по собранному HTML).

### 3. Артефакт индекса

- [ ] `manifest.json` содержит `buildId`, совпадающий с деплоем сайта. Хеши файлов сходятся.
- [ ] С `RAG_EMBEDDINGS=on` создаётся `embeddings.bin` размером `chunkCount × dim × 4` байт. Повторный билд без изменений контента делает 0 запросов к API эмбеддингов (по логу шага), а изменение одной страницы пересчитывает только её чанки.
- [ ] После деплоя `/rag/manifest.json` доступен по публичному URL. Бот больше не импортирует `bot/src/knowledge.ts`, а `bot/scripts/build-knowledge.ts` удалён или помечен deprecated.

### 4. Поиск и инструмент

- [ ] `loadRagIndex` отклоняет артефакт с неизвестным `schemaVersion` или несовпавшим хешем. Повторный вызов с тем же `buildId` не перечитывает сеть.
- [ ] Ретривер проходит unit-тесты на морфологию: «тени»/«тенью» находит страницу про тень. Лимит «не больше 2 чанков со страницы» соблюдается. Без векторов в manifest режим `hybrid` откатывается на `bm25` с предупреждением.
- [ ] `search_knowledge_base` вызывается LangChain-агентом в интеграционном тесте (с мок-моделью). Результат соответствует выходной схеме, а бюджет символов соблюдается.
- [ ] Постпроцессор помечает URL в ответе, которого нет среди результатов инструмента в этом диалоге.
- [ ] Холодная загрузка индекса (до 1000 чанков) и построение BM25 занимают меньше 1 с. Поиск (без эмбеддинга запроса) занимает меньше 20 мс.

### 5. Оценка

- [ ] Набор из ≥30 вопросов закоммичен, порог включения `hybrid` зафиксирован до настройки.
- [ ] `bm25` не хуже старого keyword-ретривера по recall@3, а на итоговом режиме recall@3 ≥ 80% (согласовано с RFC миграции). Отчёт по трём режимам лежит в `bot/eval/reports/`, а решение о режиме по умолчанию записано в отчёте.

## Дорожная карта

1. **Извлечение.** Endpoint `src/pages/rag/chunks.json.ts` для страниц и цитат, санитизация MDX, fail-fast проверки. Зависимостей нет, можно делать сразу.
2. **Чанкинг.** Разбиение, детерминированные `id`, `contentHash`, проверка URL/якорей по `dist/`. Зависит от п. 1.
3. **Артефакт.** Сначала `manifest.json` без эмбеддингов и публикация вместе с сайтом. Затем шаг эмбеддингов с кешем и CI cache. Зависит от п. 2. Публикация следует текущему деплою (GitHub Pages) и переезжает вместе с RFC Bunny без изменения контракта.
4. **Поиск и инструмент.** `loadRagIndex`, BM25, LangChain retriever и tool. Затем векторный ретривер и RRF. Переключение текущего бота с `knowledge.ts` на артефакт в режиме `bm25`, удаление `build-knowledge.ts`. Зависит от п. 3 (формат), а вектор — от эмбеддингов.
5. **Оценка.** Разметку набора можно начинать параллельно с п. 1. Прогон и решение о `RAG_MODE` делаются после п. 4. Результат передаётся в задачу `consult-telegram` RFC миграции.

## Итого и рекомендации

Строим RAG как **артефакт билда сайта**: те же Content Collections дают `dist/rag/` (чанки + manifest + опциональные кешируемые эмбеддинги) с тем же `buildId`, что и опубликованная wiki. Бот читает артефакт и отдаёт поиск LangChain-агенту как инструмент `search_knowledge_base`, начиная с BM25. Гибрид с векторами включается только по результату оценки. LLM Wiki остаётся механизмом написания базы, RAG становится механизмом её чтения ботом.

## Опциональные разделы

### Открытые вопросы

- **Провайдер эмбеддингов.** Какую мультиязычную модель берём и через кого: эмбеддинг-endpoint OpenRouter, если он доступен для выбранной модели, отдельный OpenAI-совместимый провайдер или локальная модель (`bge-m3` / `multilingual-e5`) в CI? От выбора зависит, нужен ли ключ в рантайме для эмбеддинга запроса. Решается до п. 3.
- **Пересечение с RFC миграции.** Буллит «версионированный индекс знаний» в п. 1 [RFC Bunny/Trigger.dev](./260928-pifai-bunny-trigger-openrouter.md) и «базовый поиск BM25» в п. 3 предлагается считать реализуемыми по этому RFC. Там нужно заменить их ссылкой сюда. Нужно согласие автора RFC миграции.
- **Агент или цепочка.** Слабые модели (текущая `llama-3.1-8b-instant`) ненадёжно вызывают tools. Нужен ли fallback «всегда искать по вопросу и подставлять top-k» (тот же ретривер в LCEL-цепочке)? Решение за RFC миграции, ретривер поддерживает оба варианта.
- **Follow-up вопросы.** Переформулировка запроса с учётом истории («а как это применить?») — ответственность агента или отдельный шаг query rewriting перед поиском?
- **Pagefind.** Starlight уже строит `dist/pagefind/`. Отказываемся ли мы от него как от источника для бота окончательно, или стоит сравнить его на eval-наборе как бесплатную альтернативу BM25?
- **Сырые источники `raw/`.** Индексировать ли их как второй корпус с пониженным весом? По умолчанию нет: бот ссылается только на опубликованные страницы.

### Альтернативные варианты

#### Вариант A: endpoint на Content Collections + post-build эмбеддинги (рекомендуется)

**Плюсы:** один источник правды с сайтом, полный доступ к frontmatter и YAML-цитатам, детерминированные ID. Эмбеддинги не нужны для локального билда.
**Минусы:** санитизацию MDX пишем сами.

#### Вариант B: `astro-llm` / парсинг `dist/*.html` после билда

**Плюсы:** MDX уже отрендерен, включая `<QuoteList>`.
**Минусы:** теряются структурные метаданные (автор, темы, раздел). Цитаты дублируются в HTML тематических страниц. Мы зависим от вёрстки темы Obsidian.

#### Вариант C: доработать `bot/scripts/build-knowledge.ts`

**Плюсы:** минимум изменений.
**Минусы:** второй независимый парсер контента рядом с Astro, генерация TS-кода в репозиторий, рассинхрон версий с сайтом сохраняется.

#### Вариант D: FAISS / hnswlib / внешняя vector DB (Turso, Vectorize)

**Плюсы:** масштаб на десятки тысяч документов.
**Минусы:** при сотнях чанков это лишняя инфраструктура и бинарные зависимости в рантайме. Решение откладываем до роста корпуса больше ~20 тыс. чанков.

**Рекомендация:** вариант A. Контракт `manifest.json` + `chunks.json` + `embeddings.bin` позволяет позже заменить хранилище векторов (вариант D), не меняя инструмент.

### Как это обычно делают с Astro + Starlight

1. **Источники данных**  
   У тебя уже есть Content Collections (md/mdx + yaml). Всё это доступно через `getCollection()` / `getEntry()` во время билда.

2. **Генерация артефактов на билде**  
   Самые чистые способы:
   - **Astro Endpoint** (рекомендую):

     ```ts
     // src/pages/rag-index.json.ts
     import { getCollection } from 'astro:content';
     import { Markdown } from 'astro'; // или свой парсер

     export async function GET() {
       const docs = await getCollection('docs'); // или как у тебя называется
       const chunks = [];

       for (const doc of docs) {
         // 1. Рендерим body в plain text / markdown
         // 2. Делаем chunking (по заголовкам, по параграфам, RecursiveCharacterTextSplitter и т.д.)
         // 3. Добавляем метаданные
         chunks.push({
           id: `${doc.id}#chunk-0`,
           slug: doc.slug,
           title: doc.data.title,
           content: '...',          // текст чанка
           // embedding?: number[], // если хочешь считать на билде
           metadata: { ... }
         });
       }

       return new Response(JSON.stringify(chunks), {
         headers: { 'Content-Type': 'application/json' }
       });
     }
     ```

     После `astro build` файл появляется в `dist/rag-index.json`.

   - **Интеграция Astro** или хук `astro:build:done` — то же самое, но можно писать файл прямо в `dist/` или в отдельную папку.

   - Отдельный скрипт `node scripts/build-rag.js`, который запускается после `astro build` (или параллельно через `npm-run-all`).

3. **Что именно генерировать**

   | Вариант                             | Плюсы                                                        | Минусы                                                    |
   | ----------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------- |
   | Только JSON с чанками + метаданные  | Просто, быстро, размер маленький                             | Эмбеддинги считает бот при старте                         |
   | JSON + precomputed embeddings       | Бот стартует мгновенно, нет повторных расходов на эмбеддинги | JSON сильно раздувается (особенно text-embedding-3-large) |
   | FAISS / HNSW индекс + docstore.json | Максимальная скорость поиска                                 | Нужно уметь сериализовать/загружать индекс в Python/JS    |

   Для Telegram-бота на LangChain чаще всего достаточно **первого или второго варианта**.

4. **Как бот это использует**

   ```python
   # при старте бота
   with open("rag-index.json") as f:
       data = json.load(f)

   docs = [Document(page_content=c["content"], metadata=c) for c in data]
   vectorstore = FAISS.from_documents(docs, embeddings)  # или MemoryVectorStore
   # дальше обычный RAG-ретривер
   ```

   Или, если эмбеддинги уже посчитаны:

   ```python
   # создаёшь FAISS из готовых векторов + текстов
   ```

### Сравнение с текущим «wiki llm Карпаты»

Подход Карпаты (весь текст в контекст / большой prompt) хорошо работает, пока база маленькая.  
RAG на билде даёт:

- масштабируемость (можно держать сотни/тысячи статей);
- точные ссылки на источники;
- меньше галлюцинаций на длинных ответах;
- возможность комбинировать с Pagefind-индексом Starlight (если хочешь гибридный поиск).

### Практические советы именно под твой стек

- YAML-цитаты тоже положи в отдельную коллекцию или просто прочитай файлы через `fs` в endpoint’е.
- Chunking лучше делать по `#`/`##` заголовкам + небольшой overlap — так бот будет давать более точные цитаты.
- Если контент обновляется редко — считай эмбеддинги на билде (OpenAI / local sentence-transformers / bge). Если часто — оставляй только текст.
- Можно положить `rag-index.json` в `public/` или в отдельный артефакт CI, который потом копируется к боту.
- Есть готовые штуки вроде `astro-llm` (генерирует llm.txt / контекст для RAG после билда).

### Итог

Да — **RAG в виде JSON, собираемый во время билда Astro — нормальный и распространённый паттерн**.  
Он отлично стыкуется с Content Collections + Starlight и с LangChain-ботом.  
Самый простой старт: endpoint `rag-index.json.ts` → чанки + метаданные → бот загружает JSON при старте и строит векторный индекс.

**Да, готовые компоненты есть**, но полностью «из коробки под Astro + LangChain» — почти нет. Большинство решений либо:

- готовят **текст/чанки** на билде (и дальше ты сам делаешь эмбеддинги),
- либо считают эмбеддинги в отдельном скрипте/CI,
- либо работают в экосистеме Next.js / общего SSG.

### Практика именно с LangChain

В экосистеме LangChain **нет официального “build-time RAG plugin”**, но есть устоявшиеся паттерны:

1. **Самый распространённый**  
   На билде (Astro endpoint / post-build script) генерируешь:

   ```json
   [
     {
       "id": "...",
       "content": "...",
       "metadata": { "source": "...", "title": "..." }
     }
   ]
   ```

   Потом в боте:

   ```python
   from langchain_community.document_loaders import JSONLoader
   from langchain_community.vectorstores import FAISS
   # или Chroma, MemoryVectorStore и т.д.

   loader = JSONLoader(file_path="rag-index.json", jq_schema=".[]", text_content=False)
   docs = loader.load()
   vectorstore = FAISS.from_documents(docs, embeddings)
   # или load_local(), если уже сохранил индекс
   ```

2. **С предвычисленными эмбеддингами**  
   На билде считаешь векторы → сохраняешь:
   - `documents.json` + `embeddings.npy` / JSON с векторами
   - или сразу `FAISS.save_local("faiss_index")`  
     Бот просто делает `FAISS.load_local(...)`.

3. **CacheBackedEmbeddings** (LangChain)  
   Полезно, если эмбеддинги считаешь не на каждом билде, а кэшируешь (`LocalFileStore`). Многие используют именно это + incremental update.

4. **Примеры из реальной практики**
   - Блоги на Astro/Next.js, которые на `astro build` / `next build` генерируют `docstore.json` + HNSW/FAISS индекс.
   - Ask Astro (Astronomer) — индексирование через Airflow + LangChain, но это уже оркестрация, а не чистый build-time.
   - Много проектов просто кладут готовый FAISS/Chroma в репозиторий или в артефакт CI.

### Рекомендация под твой стек

1. **Быстрый старт** → `astro-llm`  
   Получаешь чистый текст, готовый для RAG. Дальше в LangChain-боте обычный `TextLoader` / `DirectoryLoader` + chunking + FAISS/Chroma.

2. **Оптимальный контроль** → свой endpoint:

   ```ts
   // src/pages/api/rag-index.json.ts  (или просто rag-index.json.ts)
   export async function GET() {
     const docs = await getCollection("docs");
     // chunking + metadata
     return new Response(JSON.stringify(chunks));
   }
   ```

   После билда файл лежит в `dist/`. Бот его скачивает или берёт из артефакта.

3. **Если хочешь fully precomputed**  
   Добавь в `package.json`:
   ```json
   "build": "astro build && node scripts/build-rag-index.js"
   ```
   В скрипте — LangChain (или sentence-transformers) → FAISS → сохраняешь папку `rag-index/`.

Хочешь — могу набросать конкретный минимальный пример под твой Astro + Starlight + LangChain Telegram-бот (endpoint + загрузка в боте).
